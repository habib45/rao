# F11.5 — Orphan Upload Cleanup on Product Edit

**Status:** ✅ Implemented (June 2026)
**Phase:** 11.5 — Operational hygiene follow-up to Phase 11.4
**Scope:** Filesystem only. No schema change. No new gateway endpoint.

---

## Problem

The admin product-edit PATCH route replaces images by deleting every existing row in `product_images` (via `DELETE /api/products/:id/images`) and re-POSTing the incoming list. The `product_images` rows are removed, but the underlying files under `public/uploads/products/...` are never unlinked. Over time, this leaves behind an unbounded set of orphan files that:

- Consume disk space (Phase 21 reported 3.7 MB across 32 files at last check).
- Are invisible to the admin UI (they were "removed" from the post).
- Cannot be reliably GC'd by a cron because we have no `WHERE product_id IS NULL` row to look at — the rows are gone.

A duplicate-image dedup pass (F11.4.1) does not solve this; it only prevents adding new duplicates, it does not clean up what already exists from past edits.

## Goal

When an admin removes an image from a product and saves, the physical file under `public/uploads/...` is also unlinked — but only if it is safe to do so.

## Design

A pure helper, `removeOrphanUploads`, is called from the PATCH route after the gateway write succeeds. The helper diffs the previous image URL list against the new one and unlinks the local files that were dropped.

```
previous: [a.jpg, b.jpg, c.jpg]
next:     [a.jpg, c.jpg]
unlink:   b.jpg
```

### Safety properties

1. **External URLs are ignored.** Anything that does not start with `/uploads/` (e.g. `https://m.media-amazon.com/...`) is left alone. Amazon CDN URLs we never own.
2. **Path-traversal is rejected.** A URL like `/uploads/../../../etc/passwd` is rejected by `resolveSafeUploadPath()` which verifies the resolved path stays inside the uploads root and rejects null bytes and percent-encoded `..` segments.
3. **ENOENT is a no-op.** If the file is already gone, the unlink is treated as success (idempotent re-runs).
4. **Shared images are preserved by default.** If the same URL appears in another product's images, the file must NOT be deleted. Without a "where is this URL referenced?" oracle, the helper conservatively preserves any URL that is not provably unique to the just-edited product. A future gateway endpoint can pass an `isUrlStillReferenced(url): Promise<boolean>` oracle for full coverage.
5. **Never throws to the admin client.** The cleanup runs after the gateway write has already succeeded. All errors are caught, logged with structured payload, and swallowed. The admin sees a successful save regardless of cleanup outcome.
6. **Feature-flag gated.** `FEATURE_REMOVE_ORPHAN_UPLOADS` (default `false`) gates the cleanup. One release cycle of opt-in before default flip.

### Helper API

```ts
// src/lib/uploads/remove-orphan-uploads.ts
export interface RemoveOrphanOptions {
  previous: ReadonlyArray<{ url?: string | null }>;
  next: ReadonlyArray<{ url?: string | null }>;
  uploadsRoot?: string;              // default: process.cwd() + "/public/uploads"
  isUrlStillReferenced?: (url: string) => Promise<boolean>;
}

export interface RemoveOrphanOutcome {
  unlinked: string[];                // successfully deleted
  failed: { url: string; error: string }[];
  unsafeIgnored: string[];           // path-traversal / null byte
  preservedShared: string[];         // shared with another product (oracle)
  externalIgnored: string[];         // https:// or other non-/uploads/ URLs
}

export async function removeOrphanUploads(
  opts: RemoveOrphanOptions
): Promise<RemoveOrphanOutcome>;

export function isRemoveOrphanUploadsEnabled(): boolean;

export function resolveSafeUploadPath(
  url: string,
  uploadsRoot: string
): string | null;
```

### Wiring in PATCH route

```ts
// After the gateway DELETE+POST loop, before returning success.
if (isRemoveOrphanUploadsEnabled()) {
  try {
    const outcome = await removeOrphanUploads({ previous: previousImages, next: images });
    if (outcome.unlinked.length || outcome.failed.length || ...) {
      console.info("[product-images] orphan cleanup", { productId: id, ...outcome });
    }
  } catch (err) {
    console.warn("[product-images] orphan cleanup threw", err);
  }
}
```

`previousImages` is captured BEFORE the gateway write by issuing a `GET /api/products/:id`. If the GET fails, the helper is skipped entirely (no previous list → no orphans detected).

|---|---|---|
| `FEATURE_REMOVE_ORPHAN_UPLOADS` | `false` | Master switch for orphan cleanup. Off by default for one release cycle to collect logs. |

## Out of scope (deferred)

- A "where is this URL referenced?" gateway endpoint for full cross-product safety. Until then, identical URLs across products are preserved.
- A cron / scheduled janitor for legacy orphans that already exist. Run a one-off `scripts/cleanup-orphan-uploads.mjs` against the live tree, gated by `DRY_RUN=true`.
- Cleanup on `DELETE /admin/api/products/:id` (whole product deletion). The DB `ON DELETE CASCADE` already removes the rows; the files are still orphan. Same helper can be wired in `DELETE` after this feature lands.

## Rollback

Set `FEATURE_REMOVE_ORPHAN_UPLOADS=false` (or unset). The PATCH handler returns to its previous behavior — files are never unlinked, rows are still replaced.

## Observability

```
[product-images] orphan cleanup {
  productId, unlinked[], failed[], unsafeIgnored[],
  preservedShared[], externalIgnored[]
}
```

Soft anomalies to alert on: `unlinked.length > 10` per save (mass deletion — likely a bug or bulk edit), `failed.length > 0` (any I/O error deserves a look).
