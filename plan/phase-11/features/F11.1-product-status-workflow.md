# F11.1 — Product Status Workflow

## Goal
Introduce an explicit lifecycle for products so publication requires admin approval rather than being a single `is_active` toggle.

## Lifecycle
```
draft ──submit──▶ pending_review ──approve──▶ approved ──publish──▶ published
  ▲                                 │                   │
  └─────────────reject──────────────┘                   │
  ▲                                                     │
  └──────────────────── (future: unpublish) ────────────┘
```

## Database Changes — `supabase/migrations/00009_product_workflow.sql`
- New enum `product_status` with values `draft`, `pending_review`, `approved`, `published`.
- `products.product_status product_status NOT NULL DEFAULT 'draft'`.
- `products.rejection_reason TEXT NULL`.
- `products.submitted_by TEXT NULL` (email string; no FK, service role writes it).
- Partial index on `product_status` for `pending_review` and `approved` to keep the review queue + scheduler fast.
- Backfill: `published` where `is_active=true`, `draft` otherwise.

## API Routes
All three routes are POST, service-role, admin-required, no body (route 1 and 3) / small JSON body (route 2).

### `POST /admin/api/products/[id]/approve`
- Guard: `requireAdmin()`.
- Verifies row currently has `product_status='pending_review'`; 409 otherwise.
- Updates `{ product_status: 'approved', rejection_reason: null }`.
- Returns 200 with updated row.

### `POST /admin/api/products/[id]/reject`
- Body: `{ reason: string (>=5 chars) }`, Zod-validated.
- Guard: `requireAdmin()`.
- Verifies row currently has `product_status='pending_review'`; 409 otherwise.
- Updates `{ product_status: 'draft', rejection_reason: reason }`.
- Returns 200.

### `POST /admin/api/products/[id]/publish`
- Guard: `requireAdmin()`.
- Verifies row has `product_status='approved'`; 409 otherwise.
- Updates `{ product_status: 'published', is_active: true, publish_at: null }`.
- Returns 200.

## Zod Schema Update (`src/app/admin/_lib/schemas/product.ts`)
```ts
product_status: z.enum(['draft','pending_review','approved','published']).optional(),
```

## Domain Type Update (`src/types/domain.ts`)
```ts
product_status?: 'draft'|'pending_review'|'approved'|'published';
rejection_reason?: string | null;
submitted_by?: string | null;
```

## Scheduler Update (Phase 9)
`getScheduledProducts()` adds `.eq('product_status','approved')` so only approved rows are eligible to be auto-published. Keeps the cron-based `publish-scheduled` Edge Function correct.

## Review Queue Page (`/admin/products/review`)
Server component that fetches products where `product_status='pending_review'`, renders a table:
- Thumbnail, name (en), ASIN, submitted_by, submitted_at (updated_at).
- Actions per row: Approve button (POST approve) and Reject button (opens a small dialog with a reason textarea, POST reject with reason).

## AdminShell Sidebar
New link `Review Queue` with a lucide `Inbox` icon and a numeric badge showing the pending count. Count is fetched server-side in the shell wrapper (passed as prop).

## Edge Cases
- Rejected products remain visible in the regular products list (they're just `draft` again) with the `rejection_reason` surfaced on the edit page so the author can iterate.
- Publishing clears `publish_at` so the scheduler doesn't double-fire.
- Approve/Reject from a non-pending state returns 409 to prevent race conditions.
